# claude_reamde

Running context for Claude sessions working on **NetPortal**. If you're a Claude instance picking this up on a new host/instance: read this whole file before touching anything. It exists so you don't have to re-derive things the hard way — several of the notes below cost real debugging time to learn.

## What NetPortal is

A browser-based network lab virtualization platform: SvelteKit (Svelte 5) frontend, FastAPI backend (async SQLAlchemy, Alembic), PostgreSQL, Caddy reverse proxy, QEMU/KVM + Docker + Dynamips for node virtualization. Runs on Ubuntu 24.04.

## The repos

| Repo | What it is |
|---|---|
| [`net2.0`](https://github.com/nshelke23/net2.0) | **The only source of truth.** Backend, frontend, `deploy.sh` (the installer), build scripts. Every other repo below is a *build output* of this one — never hand-edit a deployment artifact directly, the fix dies on the next rebuild. |
| [`netportal-bare`](https://github.com/nshelke23/netportal-bare) | The `netportal-X.Y.run` installer, for a server that already has Ubuntu 24.04 — run it directly. |

| [`netportal-vmware`](https://github.com/nshelke23/netportal-vmware) | Unattended installer ISO for Hyper-V/VMware/any hypervisor — installs onto the VM's own disk, like a Windows/Ubuntu install ISO. Split into 2 parts (GitHub's 2GB asset cap). |
| `claude_reamde` (this repo) | This document. Update it when you finish meaningful work so the next session doesn't start cold. |

### How a change propagates

```
net2.0 (the code)
   │  deploy/scripts/build-run.sh
   ▼
netportal-X.Y.run ──────────────────► netportal-bare (published as-is)
   │                         │
   │ build-qcow2.sh          │ build-vmware-iso.sh
   ▼                         ▼
netportal-qcow2          netportal-vmware
```

Fine-tune features in `net2.0` only. To ship a new release: bump the version banner in `deploy.sh`, `build-run.sh`, then feed the resulting `.run` through `deploy/scripts/build-qcow2.sh` and `deploy/scripts/build-vmware-iso.sh` (both live in `net2.0/deploy/scripts/`, both take `--run <path>`).

## Architecture facts worth knowing

- **Filesystem**: app code at `/opt/netportal/`, secrets/config at `/etc/netportal/backend.env`, all runtime state (labs, images, templates) at `/var/lib/netportal/`, logs at `/var/log/netportal/`.
- **Services**: `netportal-backend` (uvicorn, 127.0.0.1:8000), `caddy` (:80, reverse-proxies `/api/*` and `/ws/*` to the backend, serves the static SPA), `postgresql`, `docker`. Plus `netportal-postboot`/`netportal-bridge-cloud-learning` (bridge-cloud network re-provisioning after reboot) and `netportal-mem-tuning` (KSM/swappiness).
- **Install**: `deploy.sh` is an 11-stage, resumable, idempotent installer. `sudo ./netportal-X.Y.run -- -y` for fully unattended.
- **Default NetPortal login**: `admin` / `netportal` (as of v5.8 — was `root` / `netportal` before that; both the install template and the live production instance were changed).
- **Console architecture**: no Guacamole — built-in WebSocket console proxy (xterm.js/noVNC), including an admin-only real host-shell tab (added this session, server-side-enforced role gate, audit-logged).
- **Docker images used by lab nodes**: tagged `netportal-lab/*`. The "Universal VM" node type (`netportal-pktgen:latest`) is a general-purpose test client — Firefox-via-VNC, hping3/nmap/curl/iperf3/tcpdump, and `wpa_supplicant` for 802.1X testing.

## Reaching a node's console (the default, standard way — no new mgmt login)

If you (an AI session, Claude or otherwise) need to log into a lab node directly — a router, switch, Ubuntu box, FortiGate, whatever — **don't invent a separate SSH/management account for it.** NetPortal already exposes the exact same console the browser's console tab uses.

**The default method for a text-console node (telnet/serial) is the shared WebSocket session below — not a raw socket to the reported port.** This is the standard, expected way for an AI to reach a node, full stop, not one option among several. It's genuinely safe to use *while a human already has the same console open*, because both of you share the one real upstream connection instead of racing for it — see the shared-session fix a few paragraphs down for why that matters and how it was verified.

```python
import asyncio, websockets

async def main():
    uri = "ws://127.0.0.1:8000/api/console/ws/<LAB>.json/<NODE_ID>"
    headers = [("Cookie", "netportal_session=<TOKEN>; netportal_user=<USERNAME>")]
    async with websockets.connect(uri, additional_headers=headers) as ws:
        # first frame(s) are a scrollback replay if someone's already connected
        print((await ws.recv()))
        await ws.send(b"\r\n")
        print((await ws.recv()))

asyncio.run(main())
```

(Get the session cookie the normal way: `POST /api/auth/login` with `{"username": "admin", "password": "..."}`, read `netportal_session`/`netportal_user` from the response cookies.) `websockets` is present in the backend's own venv (`/opt/netportal/backend/.venv/bin/python3`) even if not on system Python.

**Why the WebSocket path specifically, and not the raw port**: several emulated console backends (VPCS most visibly, but not unique to it) accept **exactly one upstream connection**. This used to mean a second WebSocket viewer got a brand-new competing connection dialed for it too, racing the first for that single slot — whichever side connected first got silently dropped with an unexplained "Good-bye". A user hit this directly: they lost their own open console the instant an AI session connected to the same node. It looked like a NetPortal bug; the *symptom* was real but the *architecture* was the actual problem.

**This is now fixed at the WebSocket layer** (`_SharedConsoleSession` in `backend/app/routers/console.py`): the backend holds exactly one real connection per (lab, node, console type) and fans it out to every WebSocket viewer — human browser tabs and AI sessions alike. A newly-joining viewer gets a scrollback replay, input from any viewer reaches the shared upstream, and everyone sees the same output in real time. Verified live with two concurrent viewers: neither disconnected the other, and one viewer's typed input/the device's response was visible to the other in real time. No frontend change was needed — the browser already talks to this same endpoint, so existing console tabs transparently became shared-session viewers.

**What this does *not* fix**: connecting directly to the raw `host:port` from `GET /nodes/{id}/console` (e.g. with `telnetlib` straight to the reported port) **bypasses the broker entirely** and still causes the original single-slot race — that endpoint exists to discover where the console lives, not as a green light to dial it yourself outside the WebSocket path. Only use that REST endpoint for discovery; connect via the WebSocket for actual interaction.

**For a real external client (PuTTY/SecureCRT) that can't speak WebSocket**, or if you deliberately want the raw port instead: the lab has a per-lab **"External console"** toggle (`PUT /api/labs/{lab}/console-mode` with `{"external_console": true}`, read back via `GET /api/labs/{lab}/console-mode`). ON makes the browser's own console — and now, correspondingly, the whole WebSocket layer — refuse new connections (closes `4423`) rather than compete for the slot, freeing it for a raw client. It's lab-wide, not per-node: turning it on closes every open browser console tab in that lab. You should no longer need this for an AI session specifically now that the WebSocket path shares safely — it's for the genuinely-external-client case.

**SCRIPT (`/api/script/run`) joins this same shared session too — see landmine #16.** The earlier version of this section (and the "bypasses the broker entirely" warning above) predates that fix; a script's `send`/`wait` actions now go through the exact same `_SharedConsoleSession` a browser console tab uses, keyed identically, so a script can run safely against a node a human already has open, and vice versa.

**Deliberately not applied to VNC/SPICE — checked this live, don't "fix" it the same way.** Opened two independent raw TCP connections to a running node's VNC port simultaneously: both got a full, valid RFB handshake (`RFB 003.008\n`), neither disconnected the other. QEMU's VNC server already handles multiple concurrent clients correctly — the single-connection problem the telnet fix solves never existed for VNC/SPICE, so there's nothing broken to fix. It would also be a genuinely different, riskier problem to build anyway: RFB is a stateful handshake protocol (version → security → `ClientInit`/`ServerInit` → ongoing framebuffer updates), not a raw byte stream like telnet — forcing two viewers through one shared connection the way the telnet fix does would forward the second viewer's own handshake bytes into the *already-negotiated* upstream mid-stream, which could desync or break the *first* viewer's already-working session too, not just fail to help the second one. A late joiner can't be handed a "scrollback replay" either — a partial framebuffer stream isn't a usable starting picture. Doing this correctly would mean implementing a real RFB-aware proxy (terminate each viewer's handshake independently, translate their requests into the one real upstream) — legitimate in principle, but real engineering risk for a problem that doesn't currently exist. Left alone on purpose.

**The real limitation, not a missing feature**: all of this works cleanly for anything with a text console — Ubuntu, switches, routers, FortiGate CLI — because telnet is a byte stream an LLM can read/write directly, same as any other CLI. It does **not** solve "drive a Windows GUI" the same way: the secondary console there is VNC, a pixel framebuffer, not text. "Taking control" of a graphical node means driving a screen an LLM can't natively read without vision/OCR in the loop — a different, harder problem.

## AI-driven lab feature testing (`/lab-guide`)

There's a standing, repeatable procedure for "verify/build a feature on a live
lab, test it with real traffic between real nodes, write up a functional test
plan" — codified so any future AI session (this one or a fresh one) follows
the same playbook instead of improvising each time. Both pieces are **host-
local, not in this repo** (deliberate — the user chose this over committing
them to `net2.0`):

- **The blueprint itself**: `~/.claude/skills/lab-guide/SKILL.md` — a personal
  Claude Code skill, invoked explicitly via `/lab-guide <lab_path> <feature>`
  (never auto-triggered — `disable-model-invocation: true`). Encodes: how to
  reach lab nodes (via the shared console / SCRIPT, see above — never a raw
  socket), the hard-won rule to treat fetched vendor docs as a hypothesis and
  verify every concrete command/field name against the live device before
  trusting it (see landmine #17), and a locked 7-section Guide structure.
- **Per-lab ingredients folders**: `/var/lib/netportal/lab-knowledge/<lab_path>/`
  (note: keeps the `.json` suffix in the dirname — mirrors NetPortal's own
  `/var/lib/netportal/labs/<lab_path>` storage convention exactly, so the
  mapping from lab to folder is trivial and collision-free). Drop reference
  docs/links/notes here for a given lab; the skill reads everything in the
  folder before touching the lab, and writes back a "Gotchas" section (things
  learned the hard way — wrong CLI syntax a doc claimed, quirks of that
  specific device) plus a dated log of prior test runs, so each lab's folder
  gets more useful over time instead of starting cold every session.
- **The Guide's canonical structure** (also baked into `GuideDrawer.svelte`'s
  placeholder template, which is the source of truth if the two ever drift):
  `Use Case` → `Reference` → `Topology Used` → `Configuration` →
  `Test Cases & Results` (a table, always including a baseline pass case, the
  violation/negative cases, and a baseline *re-check* afterward to catch a
  false-positive that silently broke the whole path) → `Conclusion` →
  `How to Re-run This Test`.
- **First real run**: `FortiWEB.json`'s Guide — a JSON API structural-limits
  protection test (depth/value-size/key-count/malformed-JSON), built and run
  through this exact procedure before the skill existed in written form (the
  skill was written *from* that session's playbook, then FortiWEB.json's
  Guide and ingredients folder were retrofitted to match it).

## Landmines already found (don't rediscover these)

1. **`TopologyCanvas.svelte` contains 2 legitimate embedded NUL bytes** (a map-key delimiter). Plain `grep` on this file silently misbehaves — always use `grep -a`.
2. **`virt-customize --firstboot` runs *before* `multi-user.target`.** If the firstboot script invokes something that does `systemctl enable --now <unit ordered After=multi-user.target>` (deploy.sh's density-tuning stage does exactly this), it deadlocks — the unit waits for multi-user.target, which waits for the firstboot service to finish, which is waiting for the unit. `deploy.sh` already tolerates this gracefully (its own warning + continue); it's not something to "fix," just something to know about when building images this way.
3. **The opposite problem on the ISO installer**: `late-commands` in a Subiquity autoinstall run inside a `curtin in-target` chroot — an *unbooted* filesystem, not a live system. Real services (postgres, docker) can't actually start there. The real NetPortal install has to happen via a systemd unit on the target's genuine first boot, and that unit must be ordered *after* `multi-user.target` (opposite of #2).
4. **Never boot the exact file you're about to ship, then checksum it.** Booting a qcow2 writes to it (journal, machine-id). The checksum you compute before boils down to being wrong by the time you upload. Boot a throwaway copy for verification, checksum the untouched original.
5. **GitHub Releases caps a single asset at 2GB.** The ISO (~3.5GB) needs `split -b 1900M -d --numeric-suffixes=1`, uploaded as separate assets with a `cat`-to-reassemble README section and checksums for both the parts and the whole.
6. **Removing `linux-headers-*`/`linux-tools-*`/`llvm-18` from the QCOW2 build looks safe (they're genuinely unused) but isn't**: purging them makes apt try to pull a *newer kernel* as a side effect of resolving the `linux-generic`/`linux-virtual` meta-package family. That needs network mid-build and silently changes what kernel ships. Left alone on purpose — not worth ~150MB for that risk.
7. **`apt-get clean` does NOT clear `/var/lib/apt/lists`** — that's the package-index cache (250MB+), a completely separate thing from the downloaded-`.deb` cache. Both need clearing for a lean image.
8. **`pgrep -f <pattern>` inside a Bash/Monitor tool's own command string can match its own process** if the pattern text happens to also appear in the wrapper's command line (e.g. checking `pgrep -f "curl.*live-server"` while your own script's text literally contains that string). Causes an infinite "still running" false positive. Prefer checking an exact PID (`kill -0 $PID`) over a name/pattern match when scripting a wait loop.
9. **`xorriso -extract_boot_images`** gives you real, generic boot-image files (`systemarea.img`, `gpt_part2_efi.img`) instead of hand-computed byte offsets into the source ISO — use this, not manual `dd` math, so the ISO-remastering script survives future Ubuntu point releases with a different on-disk layout.
10. **`command -v a b c` in a shell script only reliably checks the first argument** in some contexts — don't trust a multi-arg existence check without verifying each one individually first.
11. **Docker Engine 29's `containerd-snapshotter=true`** stores image layers under `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs`, *not* the classic `/var/lib/docker/overlay2`. If `/var/lib/docker` looks suspiciously empty after a `docker load`, check there before assuming data loss.
12. **A `RUN ... <<'EOF' cat > file` heredoc in a classic (non-BuildKit) Dockerfile silently produces a 0-byte file.** The heredoc body doesn't make it into the `RUN` instruction's shell invocation. Use `COPY` with a separate file instead.
13. **`curl --data-binary @bigfile` can fail with "out of memory" on large uploads** (hit this on a 3.67GB ISO) — it reads the whole file into memory before sending. Use `-T`/`--upload-file` instead, which streams from disk.
14. **Renaming a NetPortal user's username isn't a plain `UPDATE`.** `users.username` is the primary key, and `labs.owner`/`pods.username` are foreign keys to it with `NO ACTION` (not `CASCADE`) — check with `SELECT confupdtype FROM pg_constraint WHERE confrelid = 'users'::regclass` before assuming otherwise. A direct rename violates the FK the moment any row references the old value. Safe pattern: insert a new row with the new username (copy every column, clear `session_token`/`session_expires` so a fresh login is required), repoint every dependent table's FK column, *then* delete the old row — all in one transaction. Renaming the account you're currently logged in as also invalidates that session no matter what, since the client's cookie still names the old username.
15. **Connecting to a node's console directly can kick the operator's own browser console off.** Several emulated devices' telnet backends accept exactly one client at a time — a second connection races the first for that slot and one side gets dropped with an unexplained "Good-bye." Check/flip the lab's "External console" toggle (`PUT /labs/{lab}/console-mode`) before connecting directly to a node — see "Reaching a node's console" above for the full story. This isn't hypothetical: it's happened, a user lost their own console the moment an AI session connected to the same node.
16. **`SCRIPT`'s console automation (`backend/app/routers/script.py`) dialed its own private raw socket per run, bypassing the shared-console broker landmine #15 fixed for the browser WebSocket path.** Several emulated devices' telnet/serial backends only ever serve one *real* client no matter how many raw sockets connect to the port — so a script racing a human's already-open console tab (or vice versa) got a successful TCP connect but **zero bytes back, ever**: no exception, empty `output`, which surfaced as a bare `failed` status with no error and nothing to explain why. Reported live exactly this way: `FortiGate — log in [QEMU-6·console] failed` with nothing else shown, while the user had that node's console open in their browser. Fixed by making `_CliSession` join the same `_SharedConsoleSession` (`_join_shared_session`, identical key) instead of `asyncio.open_connection()`; a `_QueueSink` duck-types just enough of a WebSocket (`send_bytes`/`close`) to receive the shared session's broadcast bytes onto an `asyncio.Queue`. **A false alarm caught along the way, worth remembering the shape of**: the first instinct was that `console.py`'s own `session_key = f"{data.get('id')}:{node_id}:{type}"` was itself a bug (using the `type` *builtin* instead of a `console_type` variable) — it isn't. `type` there is that endpoint's own primary/secondary console-selector **parameter**, deliberately shadowing the builtin; a node's primary and secondary console are genuinely different `host:port` connections, so that IS the correct disambiguator. A quick isolated repro (a python one-liner without the shadowing parameter in scope) produced a *plausible-looking* confirmation of the wrong diagnosis — always re-check the actual variable's scope in the real file before trusting a repro that doesn't include the exact surrounding context.
17. **Fetched vendor docs (WebFetch/WebSearch) can be thin, paraphrased past the point of accuracy, or flatly wrong about exact CLI syntax — confirmed repeatedly against a real FortiWEB 8.0.5 box.** Example: the admin guide implied `config waf web-protection-profile` was a complete command; the box rejected it — the real command needs a mode qualifier, `config waf web-protection-profile inline-protection` (Reverse Proxy deployments) or `... offline-protection`. Same pattern for `config waf json-validation` (needs `rule` or `policy` appended — two separate tables, not one). **Always verify a fetched doc's concrete command/field names against the live device's own help/error output before relying on them** — this is now a standing rule in the `/lab-guide` blueprint, not just a one-off gotcha. Also: sending a bare `?` for CLI help over the shared script console is risky — it can leave stray text in the device's input buffer that corrupts the *next* command sent (looked like duplicate/garbled command execution before this was understood); prefer `show <root> <table>` for safe, stateless recon, and treat "Command fail" on a real command guess as a normal probe response, not a fatal error.
18. **"GUI only" doesn't mean "needs a real browser" — a GUI's own JS bundle usually just tells you the REST API underneath it, verbatim.** FortiWEB's JSON-schema-file upload is documented (and CLI-confirmed: `config waf json-schema file` never exposes a content field) as GUI-only. Rather than requiring a human to click through it, `curl`-fetched the webui's Angular JS chunks and grepped them for the feature keyword — found the exact upload endpoint (`/api/v2.0/waf/jsonprotection.jsonschemafile`) and its multipart field names (`name`, `json-schema-version`, `jsonfile`) directly in a lazy-loaded component file's `submit()` method. Hit a second wall doing this: **every non-`GET` call to `/api/v2.0/...` on this webui returns `421 Misdirected Request` regardless of endpoint or payload** (confirmed with a bare empty `POST`) until an `X-CSRFTOKEN` header is present — not a cookie-based token (unlike classic FortiOS `ccsrftoken`), but one the Angular app fetches once via `GET /api/v2.0/system/state` and caches in `sessionStorage`; found via the same JS-grepping approach (the `httpInterceptor` factory literally reads `sessionStorage.getItem("csrf_token")`). Replaying that same GET call and reading `.resutls.admin.csrf_token` (yes, `resutls` — a genuine typo in Fortinet's own API) from the response unblocked every subsequent POST. General lesson, now in the `/lab-guide` blueprint: a 401/403/421 on an otherwise-authenticated state-changing call is very often a missing CSRF header, not a real capability wall — check the frontend's own HTTP-interceptor code for the header name before concluding a browser is required.
19. **A docker node's `extras.auto_internet="true"` veth (host end named `npi<node_id:04x>[hp]`, `_auto_internet_attach` in `node_runtime_service.py`) used a naming scheme the privileged helper's `validate_iface_name()` never accepted** — every lab-link veth/TAP/bridge name matches one of 4 regexes (`nve...d..i..[hp]` etc.), but this one is a different, older-looking pattern with no matching rule. Stopping such a node calls `try_link_del()` on it, which *deliberately* does not swallow validation errors (see its own docstring) — so the exception aborted `_stop_docker_runtime()` partway through, well before the runtime registry entry got cleared, even though `docker stop` itself had already run successfully a few lines earlier. Silent, compounding damage: the next start went through either `_restart_stopped_docker_container()` (reusing the still-existing container) or `_reconcile_docker_node_runtime()` (adopting it after a backend restart) — and **neither of those two paths ever re-established a node's secondary VNC console proxy or its auto-internet veth**, unlike the fresh-create path in `_start_docker_node()` which correctly does both. Net effect on **Universal VM** nodes (the only current user of `auto_internet`, template `pktgen`): the container's own internal Xvfb+x11vnc kept running fine the whole time — never the actual problem — but nothing on the host ever proxied a port to it after the very first start, so the secondary VNC console silently, permanently broke on every subsequent stop/start. Three-part fix: added the missing regex to the helper's validator, and mirrored the secondary-VNC-proxy + auto-internet-attach steps into both of the other two docker-start code paths. Diagnosed entirely from `/var/log/netportal/netportal.log` timeline correlation (a `console_ws: type=vnc → 127.0.0.1:5901` success, sandwiched between two `stop_node ... argument failed validation: iface_name` warnings ~12 minutes apart) — the log line telling you *what* failed and *when* was far more useful here than reading the code forward from `start_node()`.
20. **When threading a new bindable prop through a shared component tree, audit every *caller*, not just the obvious direct usages.** Adding `sketchActive` to `VncConsole`/`XtermConsole` and updating their two direct call sites in `ConsolePanel.svelte` looked complete — but `PacketGenConsole.svelte` (Universal VM's console) *wraps* those same two components internally, one layer removed, and was missed on the first pass. Result: a real, user-visible duplicate/dead-button bug (see the session-log entry above) that only surfaced once someone actually opened that specific node type. `grep` for every `<ComponentName` usage, not just the ones in the file you're already editing, before considering a prop-threading change complete.
21. **`systemctl reload caddy` cannot work with `admin off` in the Caddyfile — it always fails silently-ish (the reload job errors, but the OLD process keeps running untouched, so it's easy to think nothing happened rather than notice the change never applied).** Caddy's `reload` posts the new config to its admin API (`localhost:2019` by default); `admin off` disables that API entirely. Any Caddyfile change on this host needs `systemctl restart caddy` (a real re-exec reading the file fresh), never `reload` — confirmed live: `reload` failed with `dial tcp 127.0.0.1:2019: connect: connection refused` in `journalctl -xeu caddy`, and the listening port hadn't changed; `restart` picked up the new config immediately.
22. **QEMU's own `-serial telnet::PORT` / `-vnc :N` syntax binds `0.0.0.0` by default (empty host before the colon) — every lab node's console was, until this was fixed, directly and unauthenticatedly reachable by anyone who could reach the host on that port,** completely bypassing NetPortal's login and the `_SharedConsoleSession`/audit layer built earlier this session. The fix (`telnet:127.0.0.1:PORT` / `127.0.0.1:N`) is safe because the backend's own WebSocket bridge already only ever dialed `127.0.0.1` (see `console_info()`'s default `host` param) — nothing legitimate changes, only unauthenticated direct access closes. **Gotcha**: `node_runtime_service.py`'s `reconcile_orphan_qemu` path parses a running QEMU process's *own cmdline* back out to recover its console ports after a backend restart (`serial_arg.startswith("telnet::")`, `vnc_arg.startswith(":")`) — changing the launch format without updating this parser would have silently broken orphan-adoption for every QEMU node, not just failed loudly. Same lesson as landmine #20 (thread a format/prop change through every consumer, not just the obvious call site) — this time it was a *string format* being parsed back out elsewhere, not a component prop.
23. **Fortinet VM licenses do not survive cloning, even with a byte-identical disk copy.** FortiGate/FortiSwitch/FortiWeb/etc. store license + running config on a *second* QEMU disk (`image2`, e.g. `virtiob.qcow2`) — that part is a solved NetPortal problem (see "Snapshot as Image" below). But FortiOS separately binds license validation and admin-credential validation to a machine identity it computes and seals at first boot. Confirmed by mounting a source node's disk and its snapshot's disk directly with `qemu-nbd`: `vm.lic` transfers byte-identical, but the cloned boot's self-reported serial never matches the license's bound serial — even after patching the clone's QEMU `-uuid` and first NIC MAC to exactly match the source. Admin login on the clone fails with FortiOS's own **"Unable to validate the password"**, not a normal wrong-password rejection — a different, internal failure. This is Fortinet's deliberate anti-clone protection, not a NetPortal bug, and not something worth chasing further (e.g. faking SMBIOS serial) — it's unlikely to fully work and is working against the vendor's intent. Snapshot-as-Image is still correct and useful for config/data on any node type, including Fortinet's *config* — just not its license.

## Session log (what's been built)

Chronological, most recent first. Each entry is a `net2.0` commit unless noted otherwise.

- **Hardening pass: port 8006, default root password, console-bind leak, login rate limit** (`fcac99d`) — user-requested. Caddy moved from `:80`/`:443` to `:8006` (plus baseline security headers: X-Content-Type-Options, X-Frame-Options, Referrer-Policy — none were set before). `deploy.sh` Stage 3 now also sets the OS root password to `netportal`, matching the app admin's existing default-credential convention — flagged to the user first that this is a real, publicly-documented shared secret, not per-install-random; they explicitly confirmed they wanted it that way anyway. ## How to actually work here

1. Clone `net2.0`, make the change, test it against the **live running instance** (deploy the changed files directly to `/opt/netportal/` + `/var/lib/netportal/www/`, restart `netportal-backend`, rebuild+rsync the frontend) — this codebase's convention is real verification against a live host, not just "it builds."
2. `python3 -m py_compile` the backend files and `npm run check` the frontend before calling anything done.
3. Never restart `netportal-backend` carelessly — it uses `KillMode=process` specifically so a restart doesn't kill in-flight QEMU/docker/dynamips lab nodes; a plain `systemctl restart` is safe, but always verify `ps aux | grep qemu-system` afterward to confirm nothing was disrupted.
4. Commit locally with a clear message explaining *why*, not just *what*. Don't push/release without being asked.
5. **Update this file after every `net2.0` commit, not just at the end of a session** — the user asked for this explicitly. Add a session-log entry (most-recent-first) summarizing what changed and why, and a landmine entry if the commit fixed something non-obvious a future session would otherwise waste time rediscovering. Commit-by-commit is easier to keep accurate than reconstructing a batch of commits from memory later.
